#Key findings

  1. The file key is sent in clear. The payload posts the victim's Fernet key as JSON (decryption_key) over plain HTTP to hxxp://207.180.29[.]236:8080/relay[.]php, up to ten times before the first file is touched and once more at the end (stage 3 L1300–1309, L1370). One captured request is enough to decrypt every file on that host. Ransom-ISAC's annotation of the same code says the victim "can never recover without private key", which does not hold where traffic was captured. We publish a clean-room recovery tool that looks for the key in captures, memory images or pagefile.sys, checks each candidate against a .crpx0 file and decrypts. It is validated on synthetic files only.
  2. The cryptography is sound. Keys come from os.urandom, every file gets a fresh IV, the key is wrapped with RSA-4096-OAEP, no private key is embedded, and the modulus passes four standard weak-key tests. Recovery therefore depends on what leaks or survives: the key on the wire or in memory, the unencrypted remainder of every file beyond 1 MiB, originals that are deleted but never wiped, and, very likely, the shadow copies.
  3. Several parts of the attack cannot work in these builds. Lateral movement raises an exception before it starts (key.encode() on bytes, L1053). The IsDebuggerPresent check and the AMSI patch can never find their APIs. On 64-bit Windows every pointer returned through ctypes is cut to 32 bits, so ntdll unhooking, the ETW patch and the explorer.exe injection fail silently. The UAC step writes a registry key that fodhelper does not read.
  4. All seven builds of 2026-08-04 are decoded end to end. Ransom-ISAC listed these files as unanalysed and as the best independent test set for their rules. One builder produced them for affiliate 21 in 76 minutes on 2026-08-02. The rotate amount, both stage-2 keys, the drop name and several tags change per build; the RSA key, C2, notes and wallpaper do not.
  5. Detections. Five YARA rules match 7/7 builds at every stage and 10/10 synthetic encrypted files, with no hits on 47,483 local benign files. On the same corpus the published Ransom-ISAC rules miss the four EXE builds at stages 1 and 2 and all seven bootstrap scripts. KQL, EQL and ES|QL hunts are included and have not been tested on telemetry.
  6. Independent reproduction. One command rebuilds every layer with a second toolchain (Go standard library and openssl) and compares the results. They are identical (tools/reproduce_crpx0.sh).

The C2 relays, the token, the decoder design, the Fernet-wrapped configuration, the file format and the partial encryption were already published by others. Prior art lists what each source covers. This report reproduces those points byte for byte and credits them to their authors.

#Stage 1: MinGW dropper (observed)

entry runs the CRT start-up, then FUN_00402a90 (WinMain) calls FUN_004016db, which reads LOCALAPPDATA, appends \index.dll, decodes the payload, writes it with CreateFileA/WriteFile, starts it with CreateProcessA(..., CREATE_NO_WINDOW) and deletes the file (evidence/stage1-decomp.c). The written file is an executable PE despite the .dll name.

The decoder FUN_00401566 first unmasks two 64-byte tables at 0x7b3840 and 0x7b3880 with one byte each (0x7b38c0, 0x7b38c1). Then, for each of the 0x7b3820 bytes at 0x403020, it XORs with k2, rotates right by one, inverts and XORs with k1. FUN_004014f0 and the end of the decoder call GetSystemTime and GetTickCount, but the results only feed junk arithmetic (0x1a20 ^ 0x1e, * 0x37 and so on), so these builds have no expiry check. Ransom-ISAC reports one in other builds.

Validation. The output starts with MZ, its section table covers the file exactly (3,868,672 bytes, no overlay), and the size equals the dword at 0x7b3820. FLOSS emulated the decoder on its own and recovered !This program cannot be run in DOS mode. (evidence/floss.json). capa matched 18 rules (evidence/capa.json); its "create process suspended" match is a false positive, because the flag passed is 0x08000000 (CREATE_NO_WINDOW).

Each build regenerates the stub with a different .text hash, different junk constants and its own rotate amount. tools/crpx0_stage1.py therefore finds the operands by opcode pattern (0F B6 80 imm32 for key loads, 0F B6 05 imm32 31 C2 for the mask bytes, A1 imm32 39 45 for the size, C0 E8 r for the rotate) and decodes all seven builds, at image base 0x400000 for the EXEs and at the DLLs' own bases.

#Stage 2: Python-runtime installer (observed)

Strings are XORed with a single byte, using two keys that change per build (0xD3 for configuration and API names and 0xD6 for the bootstrap in the reference build; evidence/stage2_strings.txt). APIs are resolved at run time from the 0xD3 table (FUN_0040153b). The main routine FUN_00402d4e works as follows.

  1. Sandbox gates in FUN_00402a58: a debugger, PEB NtGlobalFlag & 0x70, fewer than two CPUs, uptime under 300,000 ms, less than 0x60000000 bytes (1.5 GiB) of RAM, or a C:\ volume under 50 GiB (0x7ad138 = 50.0 with a 2³⁰ divisor), followed by a four-second busy-wait. Any hit leads to Sleep(INFINITE), which stalls a sandbox instead of exiting.
  2. It sets CRPX0_EMBEDDED=1 and OFFLINE=1 with SetEnvironmentVariableA.
  3. It picks Low_Graphics_Cache, Sys_Diagnostics, Windows_Driver_Host, Update_Temp_Store or Cache_Sys at random under %TEMP%.
  4. It downloads python-3.10.11-embed-amd64.zip when IsWow64Process is true (otherwise the win32 build) and get-pip.py with WinINet. A .onion URL would be retried through tor2web suffixes .ws, .ly, .pet, .sh and .moe (FUN_00401fe7).
  5. It writes the bootstrap to \sys_service.py (exactly 0x3A0B78 bytes), unpacks the runtime with tar.exe -xf (or Shell.Application CopyHere), adds python310.zip, ., Lib\site-packages and Scripts to python310._pth, runs get-pip, upgrades pip, installs cryptography requests pywin32 and starts python.exe sys_service.py, all with CREATE_NO_WINDOW.
  6. A decoy-document download to %USERPROFILE%\Downloads exists in the code but is off in this build, because its length variable at 0x7b2038 sits in .bss.

capa matched 22 rules on stage 2, including check for time delay via GetTickCount and contain obfuscated stackstrings (evidence/capa-stage2.json).

#Bootstrap and stage 3 (observed)

The bootstrap (evidence/bootstrap.py.txt, blob removed) builds the names builtins, base64, zlib, b64decode, decompress, exec and compile from chr() calls, sets CRPX0_LOADER=1 and runs exec(compile(zlib.decompress(b64decode(blob)), __file__, 'exec')).

Stage 3 hides its configuration one level further down. _init_crypto() (L1573) decrypts ENCRYPTED_XOR_KEY with Fernet using AES_KEY_B64, and dx() (L64) XORs integer lists with the result. The Fernet token's timestamp, 1785692479, is the same number as the build's OPERATION_ID (OP_1785692479). tools/crpx0_config.py decodes all 14 dx() calls without running anything (evidence/stage3-config.defanged.json).

main (L1702) runs in this order: the UAC attempt, the mutex, persistence, the AV and EDR kill (77 process names and 56 service names, L896–940), a scan of every drive except A: and B: written to scan_report.json (exclusions at L615) together with backup deletion, then exfiltration. The exfiltration step picks five random documents and up to ten files whose names or extensions suggest credentials or keys (password, wallet, seed, .kdbx, .pem, .pfx, .env, .ovpn and similar), zips them as data_<6 hex>_<OPID>.zip and uploads the ZIP in 512 KB multipart chunks with the boundary ----CrpxBoundary. After a ten-second sleep come encryption, lateral movement, the wallpaper, the HTML note and a VBS that deletes the payload. Geolocation through ip-api[.]com and ipinfo[.]io with User-Agent curl/7.64.1 happens when the module loads (L474–506). The bootstrap's anti-analysis (L347) covers debugger checks, timing checks, a million-call API loop, a 50,000-call API flood, hardware breakpoints, VM MAC prefixes, sandbox files, user and host keywords and the vmtoolsd and VBoxService processes, then ntdll unhooking and the AMSI and ETW patches (see Implementation faults for which of these work).

The note claims "AES-256 + RSA-2048"; the code uses AES-128 inside Fernet and RSA-4096. The note also says a copy of all the victim's data was taken; the code uploads at most 15 files.

#Encryption and file format (observed)

  • One key per run: Fernet.generate_key(), which is os.urandom(32) (L1298). Fernet is AES-128-CBC with a random IV per call and an HMAC-SHA256 tag.
  • The key is wrapped once with the embedded RSA-4096 public key using OAEP-SHA256. The key's SPKI SHA-256 is db4f490f5376d57c8cac03fee8f7dae22f8d869380eafde6c8e21bd30ea7ce0c in all seven builds.
  • For each file (L1335–1350) the payload reads the first 1 MiB, encrypts it and writes u32 rsa_len (512) | rsa_blob | u64 token_len | Fernet token | rest of the file unencrypted to <name>.crpx0. It then restores the access and modification times and removes the original with os.remove(). Up to 32 threads work through a shuffled target list; the AMSI and ETW patches are reapplied every 40 to 60 files and junk temp files are written every 10 to 20.
  • About 120 extensions in seven categories are targeted (L428). Virtual disk formats (.vmdk, .vhd, .vhdx, .qcow2, .vdi), .iso and SQL Server data files (.mdf, .ldf, .ndf) are not.

tools/crpx0_decrypt.py is a clean-room tool and shares no code with the malware. inspect prints the header and the encryption time from the Fernet timestamp. keyhunt reads PCAPs, logs, memory images, pagefile.sys or hiberfil.sys of any size and looks for the JSON field or, with --any, for every key-shaped token; each candidate is checked against the file's HMAC before it is used. decrypt takes a key or an RSA private key, and salvage writes out the unencrypted remainder. The tool never writes in place and never deletes.

It passes 15 checks on synthetic fixtures built with our own Fernet key and our own RSA-4096 key pair (tools/crpx0_decrypt_test.py, evidence/decrypt_test_summary.json). The fixtures range from 0 bytes to 3 MiB around the 1 MiB boundary. The key is found among decoys in a proxy-style log and in a 53 MiB memory-style image, wrong keys and a tampered token are rejected, and the inputs are left untouched. The tool has not been used on a real victim's files.

#Implementation faults

The full table, with a VM test for each item, is in evidence/implementation-faults.md.

#A. Cryptography: no exploitable flaw

No stage of any build contains a private key. get_env_key() is defined at L334 and never called. The RSA modulus has no factor below 2·10⁶, and Fermat factoring (2·10⁶ iterations), Pollard p−1 (B1 = 10⁶) and the ROCA fingerprint test all come back negative (evidence/rsa-key-checks.json).

#B. Faults established from the code

D1, lateral movement cannot run. domain_encrypt_network(fernet, key) calls key.encode() on key, which is bytes (L1053). bytes has no encode method, so an AttributeError is raised before domain discovery, the ARP and /24 sweeps, share encryption, the WMI and schtasks push and the SYSVOL script. The exception is reported to the C2 as propagation_error. All seven builds contain this line.

D2, the IsDebuggerPresent check and the AMSI patch are dead. Their three integer lists (L99, L291–292) decode to garbage with the build key. Solving each list against the name in its comment gives a different key per list, and two lists do not even match their names in length. The lists are byte-identical in all seven builds, while every other list is re-keyed per build. resolve_api finds nothing and both functions return.

D3, the evasion layer fails on 64-bit Windows. GetModuleHandleW, LoadLibraryW, GetProcAddress and VirtualAllocEx are called without a restype (L74–77, L259, L1604, L1643), so ctypes treats each return value as a 32-bit int. Stage 2 installs the amd64 Python whenever IsWow64Process is true, and on 64-bit Windows module bases lie above 4 GB, so handles and addresses lose their upper half (Figure 4 and evidence/ctypes_truncation.txt). resolve_api returns None, and ntdll unhooking, the ETW patch, the waitable-timer sleep and the explorer.exe injection fail inside their try/except blocks. Commands then run through subprocess as children of python(w).exe.

D4: inject_into_explorer returns 0 even when CreateRemoteThread fails (L1651–1657). On 32-bit Windows, where D3 does not apply, a failed injection still counts as success and the command never runs.

#C. Expected, not yet confirmed

D5, the UAC step does not elevate. It writes HKCU\Software\Classes\ms-settings\shell\open<6 hex>\command and runs subprocess.run('fodhelper.exe') (L972–999). fodhelper uses the open verb, so the suffixed key is ignored, and CreateProcess on an auto-elevating binary is expected to fail with ERROR_ELEVATION_REQUIRED. There are two possible outcomes. If the call raises, the payload carries on without elevation and leaves the registry key behind. If fodhelper starts, the function returns True and main exits without encrypting anything (L1707–1708). Which of the two happens is the one open question worth testing; a small harness in a clean Windows VM answers it without the sample.

D6 follows from D5. Deleting shadow copies and the backup catalog, killing AV processes, stopping services and creating the ONLOGON task all need admin rights. On a host with default UAC settings these steps fail, unless the victim started the dropper elevated or UAC is off.

Two smaller issues: run_capture reads the command output 0.5 seconds after WinExec returns, before the command has finished (L1660–1679), and the C:\\Temp-style exclusions contain doubled backslashes and never match (L619–623; harmless, since Temp is listed as well).

#Seven builds, one builder

tools/crpx0_crosssample.py runs the full pipeline over all seven builds. Affiliate 21, the RSA key, both relays, the token, both notes, the wallpaper, the 14 dx call sites, the mutex stem and faults D1 to D4 are the same in every build. The OPERATION_ID, both stage-3 keys, the AMSI and ETW patch keys, the exclusion tag and the decoy name change, as do the stage-1 rotate amount (1, 2, 4, 6 or 7), the stage-2 XOR keys (D3/D6, 77/A1, D3/79, EA/7F, 3C/FB, 0F/13, 69/25) and the drop name (index, store, sync or core.dll). The "ROL 1" in Ransom-ISAC's write-up is one value in this range: ROR 7 equals ROL 1, as in build 0dc6a5ce.

#Prior art and what is new here

Notes on each source are in evidence/prior-art.md.

The most complete earlier work is the Ransom-ISAC Research Team's "CRPx0 ClickFix Ransomware Analysis" (2026-08-27, with Bridewell, Barricade Cyber Solutions and Crystal Intelligence). It covers other builds (affiliates 1 and 20): the ClickFix lures, the chain from stager to data.dll to Python, the decoder, the Fernet-wrapped configuration, the HTTP relay, the onion /api.php path, the token, the file format, partial encryption, exfiltration, the list of anti-analysis functions, fodhelper, lateral movement, expiry kill switches, 11 YARA rules and Sigma rules. It names the seven builds analysed here as unanalysed, and the MalwareBazaar reporter of 28685dff… appears to be one of its authors. ProVendata lists 28685dff… as the "Affiliate EXE stager" and describes the RSA-4096 and 1 MB scheme. TheRavenFile lists the onions and the Tox and Session IDs. KELA, Fortra, Aryaka, The Register and Bitdefender cover the actor. ThreatFox had no entry for the relay IP or the onion on 2026-10-15.

New in this report:

  • the seven builds decoded end to end, and what the builder changes per build;
  • the builder timeline;
  • the clear-text key as a recovery path, with a tested tool;
  • D1, lateral movement cannot run;
  • D2, the anti-debug and AMSI code is dead;
  • D3 and D4, the 64-bit ctypes truncation that disables the evasion layer;
  • D5 and D6, the UAC step does not elevate (expected);
  • no expiry check in these builds;
  • the stage-2 Sleep(INFINITE) gates;
  • the wallpaper's C2PA manifest, which names ChatGPT as the claim generator and GPT-4o as the software agent (digitalSourceType: trainedAlgorithmicMedia, certificate issued to OpenAI; the signature was not verified);
  • a test of the published rules on this corpus.

On these builds we reach different conclusions from Ransom-ISAC on lateral movement (D1), IsDebuggerPresent and AMSI (D2), evasion on 64-bit Windows (D3), UAC (D5), whether victims can recover (finding 1) and the expiry check, which is absent here. Some of this may come from differences between builds; this report describes what these seven builds do.

#Open questions

  1. The outcome of D5: does subprocess.run('fodhelper.exe') raise, so the payload continues unelevated, or does fodhelper start, so the payload exits without encrypting? A harness in a clean Windows VM settles it without the sample; vssadmin list shadows afterwards checks D6.
  2. Does a live relay answer the key handshake, and does the panel echo the key back? The debug log records response bodies (L553).
  3. The sibling captcha_obf.html (MalwareBazaar 55a81d88…) probably delivered these builds and is not analysed here.
  4. The KQL and EQL hunts need telemetry from an isolated run before they are used as detections.
